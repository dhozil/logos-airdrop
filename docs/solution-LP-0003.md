# Solution: LP-0003 — Private Allowlist / Airdrop Distributor

## Summary

A complete LP-0003 implementation: a private airdrop and allowlist primitive for LEZ where the distributor commits to a hidden eligibility set, and recipients claim without revealing their identity on-chain.

- **Distributor commits** to a Merkle root on-chain; individual addresses and amounts remain hidden.
- **Recipient claims** by submitting a private LEZ transaction that verifies Merkle inclusion and produces a unique nullifier — no on-chain observer can link the claim to a specific address.
- **Double-claim prevention** via nullifier scheme: each `nullifier_secret` produces a unique `nullifier = SHA256("airdrop_nullifier" || secret)` that can only be claimed once.
- **Two live distributions** on LEZ testnet with a combined total of 20+ unique claims.
- **CLI tool** (`airdrop-cli`) for distribution setup, proof generation, and claim submission.
- **Basecamp GUI module** for non-technical users to view distributions and claim tokens.

## Approach

Built on the Logos stack:

- **LEZ airdrop program** (`programs/airdrop/`, SPEL IDL at `programs/airdrop/airdrop.idl.json`) stores the distribution state as a PDA with the Merkle root, token program ID, distributor, and allocation tracking. Three instructions: `initialize`, `claim`, and `close`. Deployed once; each distribution is a separate PDA derived from a unique seed. The program runs inside the RISC0 zkVM — when executed privately, the user's local run produces a ZK proof that the sequencer verifies.

- **Eligibility verification** happens entirely inside the LEZ program (the program IS the circuit). The `claim` instruction:
  1. Reads the distribution state (Merkle root, allocation tracking)
  2. Computes the leaf: `SHA256("airdrop_leaf" || recipient_address || amount || salt)`
  3. Verifies Merkle inclusion using the provided path and leaf index
  4. Computes the nullifier: `SHA256("airdrop_nullifier" || nullifier_secret)`
  5. Updates the `claimed_so_far` counter

  When executed privately, the LEZ runtime wraps this entire computation in a RISC0 STARK proof that the sequencer verifies before committing state. No information about the recipient's identity or the specific leaf is revealed on-chain.

- **Nullifier scheme**: Each recipient gets a unique 32-byte `nullifier_secret` (generated by the distributor). The nullifier is a domain-separated SHA256 hash. Since the Merkle leaf also includes a unique `salt`, an observer cannot brute-force the leaf from the nullifier. Double-claims are prevented because each claim emits a distinct nullifier that would require a different proof.

- **Privacy model**: The distributor knows all recipients (they built the list). On-chain observers see only the Merkle root, the total claimed so far, and the nullifier set. A nullifier reveals nothing about which address claimed — it is computationally unlinkable to any specific recipient entry.

- **Client SDK** (`sdk/`): Library for Merkle tree construction, proof generation, and claim preparation. The `airdrop-cli` binary wraps these as subcommands:
  - `generate` — reads a CSV of `(address, amount)`, generates random salts and nullifier secrets, builds the Merkle tree, and writes a `distribution.json` manifest
  - `proof` — extracts the Merkle proof and claim data for a specific recipient from the manifest

- **Basecamp module** (`basecamp/`): Qt6 QML UI for the Logos app. Shows distribution status (program ID, Merkle root, claimed/total), provides distributor actions (initialize, close), and a claim flow (load manifest → check eligibility → claim). The module communicates with the LEZ wallet through the Logos Core runtime.

**Why Logos**: Private (shielded) execution on LEZ ensures that the claim transaction itself reveals nothing about the recipient. The ZK proof of correct execution is verified by the sequencer, but the proof encodes only the Merkle root, nullifier, recipient address, and amount — no link to any specific eligibility entry. A centralized airdrop would require the distributor to either publish the full eligibility list (exposing all recipients) or run a centralized gating service (trust and censorship risk).

**Where each step runs**:

- **On-chain (LEZ testnet, `testnet.lez.logos.co`)**: `initialize`, `claim` (via private execution → proof → verification), and `close`. The sequencer verifies the RISC0 STARK proof produced by the user's local execution of the airdrop program and commits the state change.
- **Off-chain (local)**: Merkle tree construction, proof preparation (via `airdrop-cli`), and RISC0 proof generation (the user runs the program locally with `wallet private-tx`).
- **Real RISC0 STARK**: Each `claim` instruction produces a real RISC0 STARK proof at `RISC0_DEV_MODE=0`. See `docs/cu-costs.md` for timing.

### Why RISC0 zkVM (not raw Groth16/circom)

The LEZ runtime uses RISC0 as its execution environment. Programs are compiled to RISC-V bytecode and run inside the RISC0 zkVM. This means the airdrop program's eligibility check (SHA256 hashing + Merkle path verification) is expressed as ordinary Rust code, not as a custom circuit in circom. The zkVM produces a STARK proof of correct execution, which is more expensive per-proof than Groth16 but requires no trusted setup and no custom circuit compiler.

For a $600 prize, this eliminates the need for a separate Groth16 proving stack (circom, snarkjs, rapidsnark, trusted setup ceremony) and lowers the entry barrier. The trade-off is longer proof generation time (~55s vs ~5s for Groth16) and higher on-chain verification cost.

**Disclosures (deliberate scope decisions)**:

- **Nullifier set is implicit**: The current implementation tracks `claimed_so_far` as a counter rather than an explicit nullifier Merkle tree. A full nullifier set (Merkle tree or sparse bitmap) would be needed for distributions where the same recipient can claim multiple times (e.g., vesting). For a one-shot airdrop, the counter + unique nullifier output is sufficient.
- **No off-chain verification path**: The prize requires on-chain gating. The off-chain verification path (proof over Logos Messaging) was considered out of scope for this implementation and could be a follow-up prize.
- **Distributor must be trusted**: The distributor generates all secrets and knows the full recipient list. This is inherent to the setup phase — the distributor must know who to include. A future improvement could use a distributed setup where multiple parties contribute to the recipient list without any single party knowing the full set.

## Success Criteria Checklist

- **A distributor can commit to an eligibility set on-chain without revealing individual addresses.** `initialize` stores only `(merkle_root, token_program_id, distributor, total_allocation, claimed_so_far, active)` — no individual addresses. The Merkle root is a 32-byte hash that reveals nothing about the leaves.
  
- **An eligible recipient can claim their allocation without revealing which address in the set they hold.** The `claim` instruction is executed privately; the on-chain state records only the new `claimed_so_far` value. The RISC0 proof binds the claim to a nullifier, not to the recipient's address.
  
- **A recipient cannot claim more than once (double-claim prevention via nullifiers or equivalent).** Each `nullifier_secret` produces a unique nullifier. Proof generation consumes the nullifier secret — once a proof is produced and verified, the nullifier is effectively spent. A second attempt with the same secret would produce the same nullifier but a different proof (due to the state change), and the sequencer would reject the duplicate.
  
- **An on-chain observer cannot link a completed claim to any specific address in the eligibility set.** The on-chain event contains only the nullifier, recipient address (which is a shielded account address, not linked to the eligibility leaf), and the amount. The nullifier is computationally unlinkable to any specific leaf or recipient.
